# Проверка спутников и погоды на двух реальных полях

Дата проверки: 05.09.2026, UTC timestamps сохранены в JSON. Наблюдаемый период: **10–20 июня 2024 года**; история: **26 мая — 5 июля 2021, 2022 и 2023 годов**. Это проверка доступа, QA и вычислительного пути на реальных данных; независимой агрономической разметки нет.

## Провайдеры и исправления

- Sentinel-2 C1 L2A: Earth Search; scale/offset из STAC, SCL 4/5/6, медиана NDVI. Доля пригодных пикселей теперь считается относительно **всего AOI**, включая часть вне покрытия сцены. Нефизичные RED/NIR исключаются до подсчёта coverage. Версия `s2-median-scl456-scale-full-aoi-v2`.
- Landsat 8/9 C2 L2 Tier 1: Planetary Computer, 30 м, временная публичная SAS только в памяти. STAC metadata задаёт scale `0.0000275`, offset `-0.2`. Исключаются QA_PIXEL bits 0–5, радиометрическое насыщение/terrain occlusion из QA_RADSAT, fill/high aerosol из QA_AEROSOL. Версия `landsat89-t1-median-qa63-radsat-aerosol-scale-v1`. Биты сверены с [таблицей USGS](https://www.usgs.gov/landsat-missions/landsat-collection-2-quality-assessment-bands); доступ — с [официальным описанием Planetary Computer SAS](https://planetarycomputer.microsoft.com/docs/concepts/sas/).
- Погода: **Open-Meteo ERA5-Seamless**, provider `open_meteo_era5_seamless`, UTC daily, сеточная выборка у центроида. Температура поступает из ERA5-Land, осадки — из ERA5; это раскрыто в `snapshot.query.field_sources`. Исходная реализация запрашивала осадки у `era5_land`, где они не поддерживаются: live-ответ давал 11 null. Причина подтверждена [официальной таблицей переменных](https://open-meteo.com/en/docs/historical-weather-api); переход на явно выбранный `era5_seamless` дал все 11 температур и осадков у обоих полей. Температура имеет сеточный масштаб около 0,1°, осадки — около 0,25°; это не полевая метеостанция.

У Потсдама сумма осадков за выбранные 11 дней — **23,6 мм**, диапазон среднесуточной температуры — **13,6–20,3 °C**; у Севильи **6,4 мм** и **19,4–26,0 °C**. Эти значения без погодной климатологии и сведений о поливе сами по себе не доказывают засуху или тепловой стресс.

Фиксированные COG hosts проверяются allowlist; JSON-запросы запрещают redirects. GDAL самостоятельно следует перенаправлениям storage-сервера, поэтому строгий сетевой egress policy требует внешнего ограничения при публичном развёртывании. Пользовательские URL провайдерами не принимаются.

## Разбор рассчитанных рядов

Применён итоговый `ml/artifacts/final/manifest.json`; точный SHA-256 записан в [potsdam.json](potsdam.json) и [seville.json](seville.json). Расчёт выполнен `services.analysis.calculate`, тем же адаптером, который вызывает worker. Норма строится по тому же сенсору, каждый прошлый сезон даёт одно независимое годовое значение; неизвестная культура явно помечается. Межсенсорная гармонизация не заявляется.

**Потсдам.** S2 в текущем окне не дал пригодного дня, Landsat сохранил реальный анализ: NDVI **0,8020** 12 июня и **0,7654** 13 июня. Все 11 дат имеют норму Landsat по трём прошлым сезонам, центр около **0,6340**; отрицательных отклонений и событий нет. Два наблюдённых дня дополнены девятью восстановленными. Значение **0,7547** 20 июня — экстраполяция, последний реальный замер остаётся 13 июня. Статус `normal` означает выполнение порогового правила на выбранном окне, а не подтверждённое здоровье культуры.

**Севилья.** 14 июня S2 дал NDVI **0,2555**, 20 июня Landsat — **0,3232**. Изменение между разными сенсорами нельзя считать доказанным ростом растительности. Для S2 доступно только два прошлых сезона, поэтому на **10 из 11 дат z=null**; для Landsat 20 июня доступны три сезона. Его положительный z около **10,49** обусловлен малым историческим разбросом (**0,0107**) и не является агрономической оценкой. Итоговый статус — **`insufficient_data`**: алгоритм не создал негативных событий, но оценить отсутствие стресса на большей части окна по имеющейся норме нельзя. Live-проверка помогла исправить summary: `normal` теперь требует минимум двух чистых наблюдённых дней с конечным z, а не двух наблюдений и любой одной доступной нормы. Есть девять восстановленных дней и частичная ошибка исторического источника.

Для обеих территорий культура и её история неизвестны. Следующий агрономический шаг — проверить культуру/севооборот, даты уборки, полив и очные наблюдения; для проверки точности нужны размеченные длительные ряды. Эти два случая подтверждают работу второго сенсора, многолетнего сбора и честного отказа от неподдержанной нормы, но не измеряют чувствительность/специфичность диагностики.

## Воспроизведение

После установки Python workspace из README:

```sh
python scripts/live_spike.py --geometry backend/tests/fixtures/potsdam.geojson --from 2024-06-10 --to 2024-06-20 --history-years 3 --max-scenes 80 --output artifacts/live-validation/potsdam
python scripts/live_spike.py --geometry backend/tests/fixtures/seville.geojson --from 2024-06-10 --to 2024-06-20 --history-years 3 --max-scenes 80 --output artifacts/live-validation/seville
python scripts/summarize_live_validation.py --model ml/artifacts/final/manifest.json
pytest backend/tests/test_providers.py
```

Полные STAC/погодные raw snapshots находятся в `artifacts/live-validation`; их запросы, даты и hashes сохранены в компактных checked-in отчётах. `--resume` явно использует ранее сохранённые точные спутниковые запросы и заново получает погоду; без него сбор выполняется заново. Отчёт проверяет hashes и соответствие сводного ряда исходным snapshots. Повторный ответ внешнего каталога может измениться.

16 provider-тестов прошли: реальная обработка локальных синтетических GeoTIFF, QA/scale, полное покрытие AOI, записанный live Landsat STAC, память SAS, частичные данные, погода, pagination/host validation, malformed responses, Retry-After. Оффлайн-тесты не подменяют описанные выше живые проверки.
