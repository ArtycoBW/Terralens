# Улучшение TerraLens: качество NDVI при ограничении времени инференса

Дата: 05.09.2026. Исследованный commit: `31f0d97fdd6d8be3c0cc25e837ee681877526faf`.
Модель: `131aee618934151e`. Пользовательский бюджет: **до +25% времени CPU-инференса ради заметного качества**.

## Вывод и порядок действий

Наиболее перспективный путь — сохранить CatBoost и улучшить его обучающие данные, представление сенсорного контекста и обработку разных типов пропусков. Дополнительную вычислительную ёмкость сначала стоит получить оптимизацией Python/pandas. Переход на тяжёлую нейросеть сейчас имеет меньший приоритет.

Это следует из конкретных наблюдений:

1. Текущий ансамбль тратит на CatBoost вместе с сериализацией около **2%** времени; построение признаков и оформление интервалов занимают большую часть расчёта.
2. Прототип ускоренного оформления интервалов уже проверен на полном совпадении результата. Он сохраняет значения, интервалы и флаги качества всех **57 185 строк**. Числа парного замера приведены ниже; код приложения не заменён.
3. Финальная модель обучена лишь на **21 из 39 доступных полей**, по годам до 2024. Обучение на более полном допустимом train — реальная гипотеза улучшения без увеличения числа деревьев.
4. **45 худших point-прогнозов дают 21,39% суммы квадратов ошибок** текущего ансамбля. Стоит работать с резкими изменениями и несовпадением сенсоров, а не только со средним качеством гладкой интерполяции.
5. Публичная маска test почти целиком состоит из коротких пропусков. Длинные блоки остаются существенным требованием live-продукта, но их нельзя считать основным составом текущего submission.

Рекомендуемая последовательность: **интервалы и сборка признаков → обучение с отказами сенсоров → новые признаки переходов и межсенсорная калибровка → расширение final fit → условная коррекция и компактная динамическая модель**. Погодные и нейросетевые варианты — следующая очередь.

## 1. Текущее решение

Пайплайн: CSV либо live-наблюдения → маскирование и QA → сегменты поля/года/культуры → среднее соседей с ограничением gap → сезонный prior при недостатке опоры → residual CatBoost → интервалы → отдельная историческая норма и аномалии.

Финальная конфигурация: три равновесных CatBoost с seeds 42/107/211, по 400 деревьев глубины 5; 78 признаков, локальные окна 14/30/60 дней, динамика трёх NDVI-сенсоров, контекст до 14 дней для интерполированных sensor features. Погода и категориальный crop-признак в booster отключены; crop всё же влияет на разбиение и fallback-priors. Поддерживается **retrospective**. Будущие наблюдения в этом режиме допустимы; realtime сейчас явно отклоняется.

Основные точки реализации:

| Участок | Код | Следствие для исследования |
|---|---|---|
| Базовое восстановление и применение residual | [model.py](../../../ml/src/terralens_ml/model.py), `reconstruct`, строки 288–397 | Признаки и деревья считаются для всего контекста; residual применяется только к missing |
| Сборка признаков | [candidates.py](../../../ml/src/terralens_ml/candidates.py), `residual_features`, строка 95 | Много отдельных присваиваний `.loc`, повторных преобразований дат |
| Межсенсорная динамика | тот же файл, `sensor_dynamics_features`, строка 162 | Строгие соседи, локальная additive bias; более сильная калибровка ещё не реализована |
| Обучающие маски | тот же файл, `training_masks`, строка 236 | Полное покрытие целей и смесь point/block уже есть |

На одинаковых development-примерах текущая модель получила RMSE **0,068260 points / 0,094173 blocks** против **0,069207 / 0,095374** у предыдущей. На повторной assessment точки улучшились до **0,071194**, блоки ухудшились до **0,092206**; temporal blocks тоже ухудшились. Это аргумент против универсального усложнения модели без контроля режимов. Подробности: [crop-dynamics](../crop-dynamics/REPORT.md).

## 2. Какие ошибки и данные требуют внимания

### Публичный test и development

Ниже анализируется доступность контекста, а не скрытые ответы. `gap_days` соответствует текущей реализации: для внутренней даты это расстояние между опорными наблюдениями, для края — расстояние до единственной опоры. Это не длина последовательности `is_synthetic_gap` и не автоматически длина облачного эпизода.

| Gap по текущему коду | Test, N=3112 | Development points, N=4482 | Development blocks, N=4430 |
|---|---:|---:|---:|
| 0–8 дней | 2059 | 2786 | 176 |
| 9–30 дней | 1024 | 1637 | 935 |
| 31–60 дней | 29 | 59 | 2003 |
| >60 дней | 0 | 0 | 1316 |

В test доля скрытых среди первоначально известных primary составляет **14,995%**, то есть point validation с fraction=0,15 близка по общей частоте. Нет оснований утверждать, что текущая point-маска заведомо неверна. Совпадение одной частоты, однако, не доказывает совпадения облачности, границ и доступности отдельных сенсоров. В обоих CSV присутствуют только месяцы **апрель–октябрь**: смена начала сезона на сентябрь не добавит отсутствующую зимнюю историю и способна разрезать имеющийся сезон.

**3083/3112 = 99,07%** запросов имеют gap≤30 дней. Есть 122 extrapolated и 7 prior-fallback запросов. 2030 контрольных строк относятся к озимой пшенице, но это не разрешает автоматически переносить агрономическую модель зимнего сезона на анонимный CSV.

Только 464 контрольные строки принадлежат ID, встречающимся в полном raw train; 247 — ID финального обучающего selection. Подключение train-history для знакомых полей поэтому имеет ограниченный прямой охват. Для основной части test нужен перенос на новые поля.

У dynamics худший 1% development points, 45 строк, даёт **21,39% SSE**, а худший 1% blocks — **16,04%**. Систематическое смещение blocks равно **−0,01016**, в группе >60 дней **−0,02239**. Эти числа не дают права просто прибавить всем прогнозам константу: это описательная статистика после просмотра данных, не проверенная коррекция.

Источник и hashes: [data-diagnostics.json](data-diagnostics.json). Воспроизводимый расчёт: [research_gap_diagnostics.py](../../../scripts/research_gap_diagnostics.py).

### Что это меняет в приоритетах

Для submission основной фокус — короткие переходы, доверие соседям и перенос между полями. Для live нужны отдельные проверки длинных облачных разрывов и отказов источников. Не следует объединять points и blocks в произвольное среднее и затем утверждать, что это ожидаемый official score. Нельзя объявлять большие ошибки шумом и удалять соответствующие `y_true`: среди них могут быть реальные уборка, стресс и смена сенсора.

## 3. Скорость: новый профиль и проверенный прототип

Машина: Apple M4 Pro, 12 логических CPU, macOS arm64, Python 3.12.9. CatBoost использует два потока. Точные версии, hashes и повторения записаны в [profiling.json](profiling.json).

Первый запуск отдельно включает чтение CSV и проверенную загрузку артефакта. Повторные замеры используют уже прочитанный контекст и прогретую модель; исключают import/startup, запись результата, сеть и БД. Это локальный benchmark, не production p95. Старые 4,44 секунды измерены в другом запуске и не являются корректной парой для новых цифр.

Медиана повторного `predict_submission` — около **6,29 с**. Основные составляющие: признаки около **3,9 с**, интервалы около **1,6 с**, CatBoost вместе с сериализацией около **0,11 с**. [Отдельный cProfile](cprofile.txt) подтверждает десятки тысяч `.loc`-присваиваний и обход всех строк через `iterrows`; его абсолютные времена нельзя сравнивать с непрoфилированным запуском.

Замена повторной сериализации JSON на уже загруженные estimator objects дала небольшой выигрыш: медианы **6,41 → 6,25 с**, около 2,5%, при точном совпадении submission. Разница включает вариативность всего расчёта; она не является отдельным точным измерением JSON-cost. Это полезная чистка, но **она не устраняет основное ограничение скорости**.

### Прототип интервалов

В [probe_interval_speed.py](../../../scripts/probe_interval_speed.py) выбор групп выполняется массивами, а интервалы присваиваются столбцом. Исключены создание pandas Series для каждой строки и множество `.at`-операций. Сама статистическая формула не меняется.

Проверено точное совпадение полного DataFrame на 57 185 строках, включая вложенные словари интервалов и списки quality flags. Дополнительно проверены live domain shift, отсутствие calibration, unavailable/nonfinite и нестандартный индекс. Замеры идут попеременно для baseline/probe, три повтора каждого; результат — [interval-probe.json](interval-probe.json).

Сохранённый парный замер после форматирования скрипта: **4,14 → 3,05 с**, сокращение примерно **26,3%**. Проверка совпадения результатов прошла на каждом повторе. Абсолютные времена отличаются от предыдущего профиля из-за условий отдельных запусков; сравниваются только чередующиеся baseline/probe внутри одного замера. Это свидетельство полезности оптимизации, а не гарантированное production-ускорение. Прототип не установлен в production. Для переноса нужно поместить реализацию в `uncertainty.py` и включить соответствующие проверки в существующие ML/backend tests.

### Следующая оптимизация

Собирать числовые признаки в заранее выделенные NumPy-массивы; DataFrame создавать один раз. Рассчитывать календарь и сегменты один раз на вызов, а не внутри нескольких функций. Оконные counts/mean/std считать через `searchsorted` и prefix sums. Для медианы bias нужен отдельный rolling-алгоритм; нельзя молча заменить медиану средним.

Дополнительно отделить **контекст** от **дат, для которых нужны predictions**. Batch обязан сохранить все наблюдения для соседей, но не обязан формировать PI и booster predictions для каждой невыводимой даты. Сначала оптимизировать точную полную реконструкцию, затем добавить явный `query_index` в общий вычислительный слой. Простое удаление строк перед `reconstruct` разрушит контекст и изменит прогнозы.

Экономия на trees-only или ONNX ограничена измеренной долей CatBoost. Даже устранение всего этого этапа не даст большого ускорения текущего pipeline. Число контрольных дат меньше длины ряда в 18,4 раза, **но это не прогноз ускорения в 18,4 раза**: поиск контекста остаётся необходимым.

### Q1. Обучать на том контексте, который бывает в live

**Проблема.** Benchmark содержит MODIS и NDWI; live MODIS не подключён, а NDWI намеренно не передаётся из-за неизвестной формулы benchmark. CatBoost умеет принимать NaN, но это не означает, что он хорошо обучен на длительном исчезновении целого канала.

**Изменение.** Внутри train-масок добавить несколько заранее определённых режимов: текущий; без MODIS; только S2; только Landsat; без NDWI; редкие наблюдения и длинный сбой одного источника. Применять dropout к каналу/сегменту, а не только независимый Bernoulli по ячейкам. Каждый раз заново строить features из повреждённого контекста. Скрытая дата по-прежнему теряет все запрещённые динамические поля.

Не удалять качественные наблюдения из итогового пользовательского ряда: это augmentation при обучении. Можно оставить прежнее число деревьев и признаков. Новая стоимость преимущественно training-time.

**Проверка.** Point/block RMSE плюс frozen availability-slices S2-only/Landsat-only/no-MODIS/no-NDWI и разреженный контекст. Если универсальный кандидат ухудшает обычный benchmark, допустим один отдельный live-артефакт с явно своим training_scope; registry уже способен хранить версии. Два артефакта не требуют считать оба на каждом запросе.

### Q2. Учить форму перехода, а не только локальный наклон

**Проблема.** Сейчас есть две точки с каждой стороны, slopes и window mean/std. Это уже сильный набор; просто «добавить лаги» недостаточно. Хвост ошибок указывает, что скрытая точка часто отличается от гладкой линии между соседями.

**Изменение.** Добавить ограниченный набор: разность левого и правого slope; согласие знаков изменения разных NDVI-сенсоров; изменение EVI относительно NDVI; локальную амплитуду/устойчивый разброс; различие linear/PCHIP/local quadratic оценок; длительность интервала, на котором каждый slope рассчитан. Признак резкого падения должен учитывать и скорость, и расстояние во времени.

Более содержательная версия: два локальных weighted-linear fit по видимым точкам до/после gap, с малой фиксированной шириной окна; прогноз в query, disagreement и uncertainty каждого fit идут в CatBoost. Это несколько достаточных статистик, а не новая большая сеть. Не заставлять итоговый NDVI лежать между ближайшими соседями: такое ограничение может уничтожить настоящие экстремумы.

**Проверка.** Общий RMSE и p95, срезы высокой кривизны/согласованного падения/сенсорного disagreement, AOI-bootstrap. Ошибочные случаи просматривать только в development. Синтетические стресс-эпизоды проверяют сохранение формы, но не заменяют размеченные реальные события.

### Q3. Межсенсорная калибровка, учитывающая качество пары

**Проблема.** `primary_bias` — медиана `primary−sensor` на видимых парах ±60 дней, минимум три пары. Когда primary выбран из того же сенсора, часть пар тождественно равна нулю. Это не leakage, но такие пары почти ничего не говорят о межсенсорном смещении.

**Изменение.** На разрешённых видимых датах оценивать именно независимые пары S2↔Landsat, отделяя self-pairs. Начать с bias и shrinkage:

```text
b_local_shrunk = n_eff / (n_eff + k) * b_local
                + k / (n_eff + k) * b_train
```

`b_train` и `k` выбираются только внутри train folds; `n_eff` учитывает число независимых дней, качество и давность. Затем отдельной абляцией проверить affine mapping `a + b·sensor` с сильной регуляризацией slope к 1. MODIS моделировать отдельно из-за смешанных пикселей и композитов.

Не использовать сенсор скрытой target-даты как oracle. В benchmark его нельзя узнать из замаскированной строки; допустимы только выводимые из видимого контекста признаки. Не менять определение `primary_ndvi` benchmark ради удобства гармонизации. Для live физически согласованный latent NDVI и переключение источников могут потребовать собственной версии агрегации и переобучения.

**Проверка.** Co-observation leave-one-day-out, перенос по AOI, отдельные срезы смены источника, малое/большое число независимых пар. Сравнить нулевой bias, текущую медиану, shrinkage, affine. Геометрия/реальные даты могут помочь live, но отсутствующие координаты анонимного CSV нельзя придумать. Библиографический ориентир: NASA HLS [R3].

### Q4. Расширить final fit без расширения inference-модели

**Проблема.** Полное покрытие 14 977 целей относится к отобранному training_scope, а не ко всем 30 520 известным целям raw train. Старые экспериментальные ограничения продолжают исключать полезные поля и последний год.

**Изменение.** После фиксации архитектуры переобучить на большем числе разрешённых AOI и годов. Например, выделить пять AOI только под новую calibration, остальные использовать для final fit; это проектный вариант разбиения, не автоматически правильный выбор именно этих пяти полей. Сохранить прежние три модели/400 деревьев/глубину 5. Более разнообразные данные могут улучшить перенос без увеличения вычисления деревьев.

**Условие честности.** Нельзя присоединить assessment к train и продолжать показывать её прежний RMSE как оценку нового артефакта. Сначала зафиксировать процедуру и выполнить outer group/temporal backtest расширенного обучения. Затем один final refit и новая calibration для нового ensemble. Старые holdout можно переопределить как уже использованные development-данные с явной записью; получить из них «новый слепой holdout» невозможно.

Больше данных не гарантирует улучшение: распределение дополнительных полей может отличаться. Следует также проверить learning curve по числу обучающих AOI, при неизменных внешних контрольных полях.

### Q5. Условная коррекция и доверие residual

**Проблема.** Один и тот же residual booster применяется к interpolation, edge и prior regimes. В длинных blocks видна отрицательная bias; прежнее фиксированное смешивание с историей уже не прошло guardrail.

**Изменение.** Маленькая модель оценивает поправку или степень доверия к residual:

```text
y_hat = base + w(context) * residual + b(context)
```

Контекст: gap, расстояния слева/справа, наличие независимых сенсоров, disagreement, возраст/качество, fallback, признаки фазы. Регуляризовать `w` к 1, `b` к 0, ограничить сложность. Начать с нескольких coarse групп и shrinkage или десятков неглубоких деревьев. Альтернатива — добавить эти взаимодействия в основной booster, сохранив один inference artifact.

**Проверка.** Для отдельного gate нужны честные OOF-прогнозы внутри внешнего train fold. Обучить gate на всех имеющихся OOF и оценить на них же нельзя. Даже простое разбиение готового OOF по meta-folds не равно полностью nested оценке: базовые модели meta-train могли обучаться на полях meta-validation. Для строгого сравнения заново строить внутренние OOF в каждом outer fold. Не обещать пользу одной общей поправки +0,01, увиденной в таблице bias.

### Q6. Компактная модель скрытой динамики и нескольких измерителей

**Идея.** NDVI и его скорость — скрытое состояние; S2/Landsat/MODIS — разные шумные измерители. Между датами состояние развивается с учётом реального `Δt`:

```text
x_t = [vegetation_level, slope]
x_t = F(Δt) x_previous + process_noise
observation(sensor,t) = H_sensor x_t + sensor_bias + measurement_noise
```

Дисперсия измерения зависит от QA, pixel fraction, sensor spread и давности. Для retrospective — фильтр плюс обратный smoother, для будущего realtime — отдельный causal filter с учётом времени доступности наблюдения/композита. Малое состояние допускает линейную по числу дат обработку; это оценка сложности, не измеренная latency TerraLens.

Практический первый шаг — добавить оценку, дисперсию и innovation такого smoother в нынешний booster. Второй — использовать его только для заранее определённых редких/длинных gaps. Не считать state-space variance автоматически откалиброванным prediction interval; модель измерений может быть неверна.

Чтобы не сгладить уборку/стресс, отдельно проверить robust innovation либо увеличение process noise при подтверждённом несколькими сенсорами скачке. Параметры fit на train AOI. Ориентиры: Kalman и Rauch–Tung–Striebel [R2]; конкретная адаптация к TerraLens — гипотеза этого отчёта.

### Q7. Развить уже существующий Whittaker

Текущий smoother использует вторые разности на дневной сетке и Huber reweighting; по умолчанию strength=20. Это уже реализованная модель, а не новая рекомендация установить Whittaker.

Предлагаемая модификация:

```text
min_z  Σ_t quality_weight_t · ρ(y_t − z_t)
       + Σ_t lambda_t · (Δ² z_t)²
```

Уменьшать `lambda_t` возле подтверждённой смены фазы, увеличивать при слабом/шумном контексте. Начать с нескольких фиксированных режимов λ, выбранных на train/development, без десятков независимых параметров по каждому сезону. Решать ленточную систему; не строить плотную матрицу всех дат. Сначала использовать результат как feature, а не безусловно заменять текущую реконструкцию.

Асимметричное подавление низких значений может помогать против облачной примеси, но способно стереть настоящие отрицательные аномалии. Поэтому upper-envelope smoothing нельзя включать по умолчанию. Ориентир: Eilers [R1].

### Q8. Фенология и погода с осмысленным временем

Нужны не просто температура/осадки рядом с пропуском, а накопленные осадки 7/14/30 дней, число жарких/сухих дней, температурная сумма и сдвиг фазы по видимой форме сезона. Prefix sums позволяют дешёво получать несколько окон. Суммы сопровождать coverage/count, иначе отсутствующая погода станет ложной засухой.

`growing_degree_days = Σ max(0, T_mean − T_base)` — только стартовая гипотеза. `T_base` и начало накопления должны быть обоснованы культурой и доступностью данных; нельзя выдумывать дату сева. Для анонимного benchmark без координат и полной зимней истории сначала проверить, можно ли такой признак корректно определить. Если нет — ограничиться формой видимого сезона и доступными погодными окнами.

Исходная validation скрывает weather на контрольной дате: окно строится после маски, coverage явно передаётся. В live погода на оптически облачной дате может быть доступна; такой вариант оценивается отдельно от строгого benchmark-протокола. Погодная гипотеза причины стресса не становится доказанным диагнозом.

### Q9. Баланс примеров и обучение на сложных случаях

Полное покрытие целей ещё не означает равный вес: block-маски создают дополнительные примеры для некоторых целей, поля и сенсоры имеют разную плотность. Нужно посчитать вклад каждого исходного `(AOI,date)` в loss. Сравнить текущие веса с нормировкой по числу повторов цели и умеренным балансом поля/фазы/режима пропуска.

Полный inverse-field weighting может ухудшить pooled RMSE, поэтому это абляция, а не исправление по определению. Hard-example sampling строить только по внутренним train-OOF ошибкам; смешивать с обычными примерами, ограничивая максимальный вес. Не называть каждую большую ошибку ошибочной меткой, не выбирать loss только по MAE при целевом RMSE. Сравнить RMSE-loss с аккуратно настроенным robust-loss лишь как отдельный кандидат; квадрат ошибки существенно чувствителен к хвосту.

### Q10. Сильный teacher, компактный student

Небольшая temporal convolution/GRU-D, BRITS или SAITS может извлечь многоканальную динамику, которую текущие ручные признаки упускают. Но 39 независимых AOI — существенно меньше, чем число ежедневных строк; риск переобучения нельзя оценивать по 100 тысячам строк как независимым примерам.

Практический путь: обучить teacher только в train folds, получать masked/OOF прогнозы и обучить компактного student на смеси истинных целей и teacher estimates. Student может остаться CatBoost с несколькими временными признаками. Teacher не должен видеть скрытую цель при создании pseudo-label для её учебного примера. Сначала сравнить teacher с текущей моделью, затем проверить, сохраняет ли distillation его выигрыш.

До качественного teacher дистиллировать текущие три CatBoost в один малоинтересно: деревья занимают лишь малую долю времени, а часть ансамблевого качества будет потеряна. Diffusion/CSDI с многими sampling steps не подходит основным runtime-кандидатом; можно рассматривать только как дорогой offline teacher. Ориентиры: [R4–R8].

## 5. Backend: качество входа и скорость полного анализа

### Сохранить корректную семантику входных данных

Scale/offset из raster metadata, SCL для Sentinel, QA_PIXEL/QA_RADSAT/aerosol для Landsat, field-level valid fraction уже реализованы. Предлагать «добавить облачную маску» без этого уточнения неверно. Следующий шаг — проверить, какие QA-признаки сохраняются в snapshots и доходят до ML: модель сейчас получает прежде всего значения каналов, а не непрерывные веса pixel fraction/spread.

В `extract_optical_scene` общая маска `valid` пересекает validity всех прочитанных массивов, включая blue/SWIR. NDVI математически требует red/NIR и QA; недоступность auxiliary band способна уменьшать его coverage. Проверить отдельные masks по индексу и независимую пригодность NDVI/EVI/moisture index. Изменение требует новой aggregation_version и проверки старых snapshots.

Live moisture index `(NIR−SWIR)/(NIR+SWIR)` сейчас **намеренно** не переносится в benchmark NDWI-feature. Это правильная защита от несовпадения формул, а не забытый mapping. Улучшение — определить формулу из достоверного описания dataset либо обучить live-модель с отдельным явно названным каналом; слепое включение NDWI недопустимо.

### Использовать QA в модели, не превращая его в target leakage

Добавить quality ближайших разрешённых observations, количество независимых дат, покрытие пикселями и robust spread, а затем обучить/калибровать модель на реально геопривязанных рядах. В benchmark таких метаданных нет, поэтому их нельзя заполнить вымышленной «высокой уверенностью» для обучения. Начальный перенос — sensor dropout и доступность/возраст, которые доступны в обоих доменах.

### Отделить историческую норму от реконструкции

Backend присоединяет исторические строки к контексту и считает для них reconstruction, признаки, booster и интервалы, затем оставляет запрошенный диапазон. При этом в текущем CatBoost-algorithm `seasonal_history` не вызывается: `use_history=true` само по себе не включает межгодовой M4 residual. История полезна для отдельной нормы и может помогать локально в том же сегменте, но нельзя приписывать текущему booster полноценную адаптацию по всем предыдущим сезонам.

Оптимизировать расчёт запрошенных дат с сохранением необходимого контекста; историю нормы обрабатывать отдельно. Для нового исторического feature использовать только предыдущие сопоставимые сезоны и явную культуру. Кэш immutable snapshots уже есть; новые ключи обязаны учитывать geometry/config/QA/model versions.

### Измерять сетевой путь отдельно

Порог +25% нужно проверять как минимум в двух режимах: автономный batch и warm worker на готовых snapshots. Сбор нового поля зависит от сетевых запросов и raster I/O; их нельзя смешивать с CPU inference. HLS, дополнительные каналы, новая историческая погода и SAR способны увеличить ingestion гораздо сильнее, чем model.predict. Ни одна такая интеграция здесь не считается выполненной или проверенной live.

### Две недорогие по ML-вычислениям проверки покрытия

В [tasks.py](../../../backend/apps/core/tasks.py), строка 134, текущие наблюдения запрашиваются ровно на `period_from/period_to`. Для короткого выбранного пользователем интервала ближайшие хорошие наблюдения за его пределами могут не попасть в reconstruction. Проверить отдельный небольшой context buffer до/после запрошенного периода, например 14/30 календарных дней, с обрезкой только выходного ряда. Это предложение для retrospective; будущие данные запрещены в eventual realtime. Сравнить прогноз одной даты при выборе узкого и широкого диапазона. Прирост raster I/O измерять отдельно; дополнительные даты не должны незаметно менять summary периода.

В [stac.py](../../../backend/providers/stac.py), `search_scenes`, строки 172–250, есть пагинация и явный `scene_limit` warning. Но затем уже найденные сцены сортируются и ограничиваются `max_scenes`; равномерное покрытие длинного диапазона не гарантировано. Улучшение — разбиение запроса по времени и ограниченный выбор сцен по временным корзинам/качеству при том же общем лимите дорогих raster reads. Это не повод снять лимиты: сначала проверить полноту дат и корректность warnings на fixture со сценами сверх лимита. Более удачное распределение тех же наблюдений способно улучшить реконструкцию без усложнения модели.

## 6. Как поставить следующий эксперимент

### Основные правила

1. Зафиксировать baseline `131aee618934151e`, hashes, train/validation AOI, годы, маски, feature contract и бюджет до запуска кандидатов. Для сопоставимости первый этап использует прежние development folds.
2. Все динамические столбцы скрытой строки маскируются до features. Проверить invariance к изменению hidden target/sensors/weather, изоляцию AOI/культур/сезонов и отсутствие использования target-date sensor label.
3. Сохранить point и block masks. Добавить отдельные frozen missing-sensor и sparse-context проверки; не подменять ими основной benchmark RMSE.
4. Менять одну содержательную гипотезу за раз; потом проверять ограниченное число комбинаций. Не перебирать сотни вариантов на тех же 21 AOI.
5. Основная метрика — pooled RMSE. Дополнительно MAE, bias, p95, worst-decile AOI, gap/crop/sensor-availability/year/edge slices и N. Парный bootstrap по целым AOI; повторные маски и дни не независимы.
6. Рекомендуемый operational gate: ≥1% относительного выигрыша point RMSE, без ухудшения blocks, улучшение минимум в 4/5 folds, положительная нижняя граница парного AOI-bootstrap, CPU latency≤1,25 baseline. Это проектное правило выбора, не установленный пользователем минимальный процент качества.
7. На этапе расширения train/nested gating строить соответствующую nested проверку заново. Bootstrap development после выбора не устраняет selection bias. Новая независимая география/сезоны остаются самым сильным подтверждением.
8. После выбора — один final fit и отдельная calibration. Показывать coverage и ширину PI по gap/availability; не обещать безусловное conformal coverage при зависимых AOI и domain shift [R9].

### Ограниченный набор первой волны

| Кандидат | Что меняется | Что фиксируется |
|---|---|---|
| B0 | Текущий артефакт/процедура | Полный reference |
| B1 | Sensor/segment dropout | 78 features, 3×400 depth5 |
| B2 | 6–12 признаков формы перехода | Маски и прежний ensemble |
| B3 | Shrinkage sensor bias, независимые пары | Маски, глубина/число деревьев |
| B4 | Нормировка повторов исходной цели | Features/ensemble |
| B5 | Только лучшая заранее ограниченная комбинация B1–B4 | Все остальные параметры |

Параллельно подготовить скоростной рефакторинг интервалов/feature assembly с проверкой идентичности. Kalman/gating/погоду запускать второй волной по результатам срезов. Расширение final training scope оценить собственной learning curve и outer backtest; оно не должно незаметно менять сравниваемые условия B0–B5.

Для baseline и каждого runtime-кандидата: одинаковый CPU/thread budget, warm/cold замеры отдельно, чередование порядка, не менее 10 повторов для решения о latency; для заявления p95 — отдельный достаточно длинный нагрузочный прогон. Измерять read/feature/base/predict/interval/export, peak RSS, одно поле/один сезон, несколько лет истории и полный test. Наши 3–5 повторов сейчас — разведочный профиль.

## 7. Что пока отложить

- Большие Transformers/foundation models и inference-time diffusion: нет подтверждённого выигрыша на этих полях, runtime-budget ограничен.
- Полноразмерный Gaussian process для всех дат и полей: сначала компактный state-space вариант; плотная матрица и cubic fitting здесь необязательны.
- Механическое увеличение ансамбля/ONNX/quantization как главный способ ускорения: противоречит профилю текущего пайплайна.
- Возврат готовой CSV-climatology, status или zscore в признаки: происхождение неизвестно, возможно раскрытие цели.
- Автоматическое исправление outlier-targets и upper-envelope NDVI: может стирать настоящую аномалию и искажает RMSE ground truth.
- SAR, географические embedding и внешняя погода для анонимных AOI: нет координат. Для live это отдельное исследование с собственным ingestion-бюджетом.
- Безусловное использование истории культуры или смена начала сезона для всех полей: нужны реальные даты/метаданные, а не вывод только из названия культуры.

## 8. Литературные ориентиры

**Статус всех внешних ссылок этого раздела: не перепроверены в текущем сеансе из-за сетевой недоступности.** Ниже указаны известные первичные работы/официальные ресурсы и узкая причина их релевантности. Методы TerraLens и предлагаемые изменения описаны выше как собственная инженерная адаптация; численных заявлений о результате этих работ на наших данных нет.

| ID | Первичный источник | Для чего нужен |
|---|---|---|
| R1 | Eilers, *A Perfect Smoother* (2003), [DOI](https://doi.org/10.1021/ac034173t) | Penalized least squares/Whittaker; развитие уже имеющегося smoother |
| R2 | Kalman, *A New Approach to Linear Filtering and Prediction Problems* (1960), [DOI](https://doi.org/10.1115/1.3662552); Rauch, Tung, Striebel, *Maximum Likelihood Estimates of Linear Dynamic Systems* (1965), [DOI](https://doi.org/10.2514/3.3166) | Малое динамическое состояние, фильтр и retrospective smoother |
| R3 | NASA, [Harmonized Landsat and Sentinel-2](https://hls.gsfc.nasa.gov/) | Официальный ориентир по межсенсорной гармонизации; не обещание готового drop-in для CSV |

| R7 | Hinton, Vinyals, Dean, *Distilling the Knowledge in a Neural Network* (2015), [препринт](https://arxiv.org/abs/1503.02531) | Teacher/student; наша regression/distillation-схема требует собственной проверки |
| R8 | Tashiro et al., *CSDI: Conditional Score-based Diffusion Models for Probabilistic Time Series Imputation* (2021), [препринт](https://arxiv.org/abs/2107.03502) | Возможный offline teacher, низкий приоритет для runtime |

| R10 | CatBoost, [sum_models](https://catboost.ai/docs/en/concepts/python-reference_sum_models) | Возможная упаковка ансамбля; не устраняет стоимость всех деревьев и не главный bottleneck |

## 9. Артефакты и воспроизведение

Добавлены только отчёт, исследовательские скрипты и evidence; production backend/ML, опубликованная модель и submission в этой работе не заменялись.

Из корня репозитория в существующем Python-окружении:

```sh
.venv/bin/python scripts/profile_reconstruction.py \
  --output docs/analysis/quality-speed-research --repeats 5
.venv/bin/python scripts/probe_interval_speed.py \
  --output docs/analysis/quality-speed-research/interval-probe.json
.venv/bin/python scripts/research_gap_diagnostics.py \
  --output docs/analysis/quality-speed-research/data-diagnostics.json
```

Запускать замеры последовательно, без обучения/других тяжёлых вычислений. Можно передать другой `--output`, чтобы сохранить исходное evidence. Последний скрипт использует существующий локальный `artifacts/crop-dynamics/predictions.csv`; этот большой файл игнорируется Git. На чистом checkout его нужно сначала воспроизвести прежней командой `research --config ml/configs/crop-dynamics.yaml --development-only` из ML README. Профиль и interval-probe требуют только публичный test и опубликованный артефакт.

Проверки скриптов: Ruff check/format, исполнение на текущем test, точное совпадение полного результата для interval-probe, совпадение submission для cache-probe, проверка input/model/script SHA-256. Это проверки исследовательских изменений; прежние результаты 139 tests из crop-dynamics не выдаются за новый прогон всех backend/ML тестов.
