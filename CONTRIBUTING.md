# Правила разработки TerraLens

## Названия коммитов

Во всём репозитории использовать формат из примера пользователя:

```text
type(scope): описание изменения на русском
```

Тип и область — латиницей в нижнем регистре. Область обязательна. После двоеточия один пробел; описание начинается с глагола в неопределённой форме: «добавить», «исправить», «подготовить», «обновить», «вынести». Без точки в конце и без эмодзи. Заголовок кратко описывает фактически выполненное изменение; ориентир — до 72 символов.

Один коммит — одно логически связанное изменение. В заголовке не перечислять все файлы; подробности и проверки при необходимости вынести в тело после пустой строки. Не использовать сообщения `update`, `fix stuff`, `WIP` и не называть подготовку ТЗ реализацией продукта.

### Типы

| Тип | Когда использовать |
|---|---|
| feat | новая работающая возможность |
| fix | исправление ошибки |
| docs | документация и спецификации |
| refactor | изменение структуры кода без изменения поведения |
| perf | улучшение производительности |
| test | добавление или изменение тестов |
| build | сборка, зависимости, упаковка |
| ci | автоматические проверки и CI/CD |
| chore | подготовка репозитория и служебные изменения |
| style | форматирование кода без изменения логики; не новая функциональность UI |
| revert | отмена ранее внесённого изменения |

### Области

| Scope | Назначение |
|---|---|
| project | общая структура и подготовка проекта |
| docs | общая документация |
| backend | Python-сервер в целом |
| api | контракт и endpoints |
| geo | регионы и геометрии |
| ingestion | сбор и подготовка внешних данных |
| jobs | очередь и фоновые задачи |
| ml | модели, валидация и инференс |
| data | аудит и схемы данных |
| frontend | Next.js-приложение в целом |
| ui | общие компоненты интерфейса |
| map | рабочая карта |
| charts | графики и визуализация рядов |
| landing | лендинг, Ascend и его секции |
| infra | инфраструктура и окружение |

Выбирать наиболее конкретную подходящую область. Новую область можно добавить при появлении отдельного модуля; не использовать разные синонимы для одной области без причины.

### Примеры

```text
feat(ui): расширить лендинг командой и тарифами
feat(landing): добавить секции тарифов и команды
docs(backend): уточнить требования к автоматическому сбору данных
feat(geo): добавить сохранение пользовательских полигонов
fix(ml): исключить скрытые значения из признаков валидации
feat(map): добавить рисование контура поля
fix(charts): сохранить разрывы ряда при отсутствии данных
test(api): проверить изоляцию результатов между сессиями
build(frontend): обновить зависимости приложения
chore(project): подготовить основу проекта и ТЗ
```

Для несовместимого изменения использовать `type(scope)!: описание` и пояснить нарушение совместимости в теле строкой `BREAKING CHANGE: ...`. Названия squash-коммитов и вручную оформляемых merge-коммитов также должны следовать этому стилю.

## Перед отправкой

Проверить состав diff и соответствие сообщения изменению. Для Python выполнить Ruff и затронутые pytest-проверки; для frontend — typecheck, lint и проверки изменённых сценариев. При изменении API обновить `docs/openapi.json` и сгенерированные TypeScript-типы. Полный набор воспроизводит CI.

Коммиты должны описывать фактическую реализацию. Отчёты и документацию не называть новой функциональностью приложения; опубликованные метрики сопровождать протоколом и ограничениями.
